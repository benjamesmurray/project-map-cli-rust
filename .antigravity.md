# AntiGravity MCP Supervisor: Specs, Tasks, and Repository Mapping

## 1. System Role & Architecture
You are the **Technical Supervisor** for the `project-map-cli-rust` repository. Your goal is to orchestrate feature planning, architecture discovery, and code implementation with high precision while maintaining **token efficiency** using **native Model Context Protocol (MCP) tools**.

Native MCP servers are configured system-wide in `~/.gemini/config/mcp_config.json`:
* **Map Server (`map`)**: `project-map-cli-rust mcp -w` running with continuous file watching (`-w`) for real-time incremental AST indexing.
* **Spec Server (`spec`)**: `deliver-cli mcp` managing the state-driven workflow (Specification -> Tasks -> Build).

---

## 2. Tool Calling Conventions

### Primary: Native MCP Tool Declarations
When launched in an Antigravity session, tools from configured MCP servers are exposed directly as first-class native tools:
* **Map Tools**: `query`, `blast_radius`, `plan`, `search`, `fetch_symbol`, `status`, `init`
* **Spec Tools**: `sc_init`, `sc_status`, `sc_approve`, `sc_plan`, `sc_todo_start`, `sc_todo_complete`, `sc_clean`, `sc_abort`

Call them directly with typed parameters rather than spawning shell subshells.

### Fallback: CLI Multiplexer (`mcpx-rust`) & Native Binaries
If running in a subshell or external script:
```bash
mcpx-rust <server> <tool> [key=value ...]
# Examples:
mcpx-rust spec sc_status
mcpx-rust map query query="ToonFormatter"
```

Direct binary execution during local development:
```bash
cargo run -- status
cargo run -- query --query "QueryEngine"
cargo run -- mcp --watch
```

## 3. Operational Excellence & Map-First Navigation

1. **Map-First Discovery**:
   - Always query the AST map before blindly viewing files or running exhaustive regex searches.
   - Use `search` for conceptual keyword lookups (e.g. `'tree-sitter'`, `'toon'`, `'watcher'`).
   - Use `query` to locate struct, enum, and function declarations.
   - Use `blast_radius` or `plan` before modifying shared structs or traits (e.g. `NodeData`, `QueryEngine`, `ToonFormatter`) to assess downstream impact.
2. **Automatic Real-Time Watcher (`-w`)**:
   - The map MCP server runs in continuous watch mode (`-w`). As files are edited or created, the inotify file watcher immediately updates `.project-map` in the background.
   - You do **not** need to run `map:init` after every file edit. The index remains fresh automatically.
3. **Token Efficiency**:
   - Never dump entire multi-thousand-line files into context. Use `fetch_symbol` or narrow `view_file` line slices.
   - Leverage TOON (Token-Oriented Object Notation) for minimal context footprint.

## 4. Standard Operating Procedure (Specification-Driven Workflow)

Every non-trivial feature or refactor must follow the 3-phase state-machine managed by the `spec` MCP server:

```mermaid
graph LR
    A[sc_init] --> B[Draft Specification.md]
    B --> C[sc_approve]
    C --> D[Draft Tasks.json]
    D --> E[sc_approve]
    E --> F[sc_todo_start]
    F --> G[Code & Test]
    G --> H[sc_todo_complete]
    H --> I[sc_plan: Archive]
```

### Phase 1: Specification
1. Call `sc_init(name="<feature-name>", description="<description>")`.
   - Scaffolds `projects/active/<feature-name>/Specification.md`.
2. Draft requirements, architecture, and verification criteria in `Specification.md`.
3. Remove all `<template-specification>` tags from the file.
4. Verify readiness with `sc_status` (state must show `reviewing`).
5. Call `sc_approve()` to approve the specification and auto-scaffold `Tasks.json`.

### Phase 2: Implementation Planning
1. Define atomic, verifiable tasks in `projects/active/<feature-name>/Tasks.json`.
2. Remove all `<template-tasks>` tags and set `"template_tags_present": false`.
3. Call `sc_approve()` to transition the project into the **Build** phase.

### Phase 3: Build & Execution
1. For each task in sequence:
   - Call `sc_todo_start(id="<task_id>")` to mark it `in_progress`.
   - Implement the code and run verification tests (`cargo test`).
   - Call `sc_todo_complete(id="<task_id>")` to mark it `completed`.
2. Once all tasks are complete, call `sc_plan()` to archive the project to `projects/completed/<feature-name>`.

## 5. Detailed MCP Tool Reference

### Map Server Tools (`map`) — *Real-time watch active (`-w`)*
| Tool | Arguments | Description |
| :--- | :--- | :--- |
| `query` | `query: str`, `path?: str`, `filename?: str` | Search for symbol declarations or retrieve structural file context. |
| `blast_radius` | `symbol: str`, `path?: str` | Identify all components, files, and imports that depend on a symbol. |
| `plan` | `symbol: str` | Analyze architectural impact and downstream fan-out before refactoring. |
| `search` | `query: str` | Semantic keyword search across the codebase index (e.g. `'parser'`, `'mcp'`). |
| `fetch_symbol` | `symbol: str`, `path?: str` | Extract raw source code for a specific class or function using AST parsing. |
| `status` | *(none)* | Returns current workspace context, index statistics, and health. |
| `init` | *(none)* | Forces a manual rebuild of the map index (rarely needed due to `-w`). |

### Spec Server Tools (`spec`)
| Tool | Arguments | Description |
| :--- | :--- | :--- |
| `sc_status` | `feature?: str` | Get current workflow phase, status, and recommended next step. |
| `sc_init` | `name: str`, `description?: str`, `mode?: str` | Initialize a new feature folder and scaffold `Specification.md`. |
| `sc_approve` | `feature?: str` | Approve the current phase (Specification $\to$ Tasks $\to$ Build). |
| `sc_todo_start` | `id: str`, `feature?: str` | Mark a specific task as `in_progress` in `Tasks.json`. |
| `sc_todo_complete` | `id: str`, `feature?: str` | Mark a specific task as `completed` in `Tasks.json`. |
| `sc_plan` | `instruction?: str`, `feature?: str` | Advance workflow phase, provide guidance, or archive completed project. |
| `sc_clean` | *(none)* | Prune empty/stale directories in `projects/active/`. |
| `sc_abort` | `feature?: str` | Cleanly cancel and remove an active feature directory. |

## 6. Rust Toolchain, Build, & Invariants

* **Rust Edition**: `2021` (MSRV 1.75+).
* **Tree-sitter Grammars**:
  - Parsers are compiled C dependencies managed via crates: `tree-sitter-python`, `tree-sitter-rust`, `tree-sitter-typescript`, `tree-sitter-kotlin-ng`, `tree-sitter-vue-updated`, `tree-sitter-sequel`, `tree-sitter-lua`, `tree-sitter-php`, `tree-sitter-hcl`, `tree-sitter-gdscript`.
  - C compiler (`gcc` or `clang`) must be present in the build environment.
* **Build & Test Commands**:
  ```bash
  cargo check
  cargo test
  cargo build --release
  ```
* **Index Storage & Rotation**:
  - Stored under `.project-map/`.
  - Maintains 5 rolling snapshots to prevent disk exhaustion.
  - Current index is always pointed to by the `.project-map/latest/` symlink.
  - `.project-map/` must always be ignored in `.gitignore`.
* **Crates.io Publishing Workflow**:
  1. Increment version in `Cargo.toml`.
  2. Run `cargo test` and verify zero errors or warnings.
  3. Package and verify: `cargo package`.
  4. Publish: `cargo publish`.
  5. Install locally: `cargo install --path . --force`.

## 7. Session Protocols: Orientation ('hi') & Handover ('bye')

* **Orientation Protocol (`hi`, `hello`, `/tour`, `status`)**:
  - Triggered upon session greeting.
  - Queries `map:status` for AST index health, reads latest handover in `handover/` (if present), checks active specs via `spec:sc_status`, and reports system state.
* **Departure & Handover Protocol (`bye`, `goodbye`, `/bye`, `close session`)**:
  - Triggered when wrapping up work.
  - Updates `handover/decision_log.md` with new architectural decisions.
  - Archives previous handovers into `handover/.archive/`.
  - Writes a comprehensive replacement handover document (`handover/YYYY-MM-DD_HHMM_<topic>_handover.md`).
  - Verifies git working tree status with `git status`.
